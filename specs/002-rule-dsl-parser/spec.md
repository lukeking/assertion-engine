**Feature Branch**: `002-rule-dsl-parser`
**Created**: 2026-10-28
**Status**: Draft
**Input**: User description: "M1（Linear GAR-18）：不變量 DSL 與 Parser Tree。以已定稿的 17 條白話規則語料（門檻比較 4、邏輯組合 3、時序約束 6、趨勢外推 4；數字一律待定、依情境基準）反推 DSL 語法需求，手寫 recursive-descent／Pratt parser（決策 002）把規則解析成語法樹。M1 驗收：可解析基本規則（比較、邏輯運算）為語法樹；語料進版控並作為 parser 回歸測試集（憲章原則 III）。"

## Clarifications

### Session 2026-10-28

- Q: M1 完成時解析能力要到哪一階？ → A: 頂階「全語料」：17 條都要解析成語法樹；時序與視窗的語法在 M1 定，語意留給 M2／M3。
- Q: 數值單位怎麼處理？ → A: 單位寫在詞彙宣告裡（欄位、衍生量、函式、具名門檻各自宣告），解析時檢查量綱；規則文字不寫單位。
- Q（plan 階段）：語料 17 條都沒用到「或」「非」，FR-004 與 SC-006 衝突，怎麼解？ → A: M1 文法不放 `or`／`not`，先登記為保留字；
  之後有語料需要時再加入，不會讓既有規則失效。
- Q（plan 階段）：規則語法採用哪一套？ → A: 採用 [research.md](research.md) Decision 2 的語法；解析技術用 Pratt parser（Decision 3）。

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 把基本規則解析成語法樹 (Priority: P1)

作為引擎開發者，我用文字寫下門檻比較與邏輯組合的不變量（語料的前 7 條），引擎把它解析成一棵語法樹，
樹的結構忠實反映運算的先後與巢狀，讓 M2 的 Evaluator 有一個明確、不靠猜的輸入。

**Why this priority**: 這是 GAR-18 的驗收標準本身；之後的 Evaluator、視窗與 Fuzzer 都建在這棵樹上。

**Independent Test**: 對 7 條門檻比較與邏輯組合規則各自解析，將語法樹的正規序列化與回歸測試集裡的預期樹逐條比對。

**Acceptance Scenarios**:

1. **Given** `battery-floor` 的規則文字，**When** 解析，**Then** 樹根是比較節點，兩側分別是電量欄位與具名門檻。
2. **Given** 一條同時用到「且」與「若 A 則 B」的規則，**When** 解析，**Then** 樹結構依文法宣告的優先序與結合性；
   加上括號改變分組時，語法樹隨之改變。
3. **Given** `return-reserve` 的規則文字，**When** 解析，**Then** 算術、負號與函式呼叫依優先序巢狀，
   每個節點都記錄它在原文中的位置。
4. **Given** 同一份規則文字，**When** 重複解析，**Then** 語法樹的正規序列化完全相同。

### User Story 2 - 無效規則被拒，並指出哪裡錯 (Priority: P1)

作為引擎開發者，我寫錯一條規則時（括號不成對、打錯欄位名、參數個數不對），引擎拒絕它，並告訴我錯在第幾行第幾欄、錯在哪裡，
而不是默默接受一棵意思不同的樹。

**Why this priority**: 默默接受的錯規則是一個永遠不會告警的守門員——它看起來在執行，實際上什麼都抓不到，
而且和「一切正常」長得一模一樣。

**Independent Test**: 對無效規則集的每一個案例解析，確認全部被拒、沒有產生語法樹，且回報的位置指向造成錯誤的那一段文字。

**Acceptance Scenarios**:

1. **Given** 括號不成對、缺少運算元或尾端有多餘內容的規則，**When** 解析，**Then** 拒絕並回報第一個錯誤的行、欄與原因，不產生語法樹。
2. **Given** 引用未宣告名稱的規則（欄位打錯字、未知函式、未宣告的具名門檻），**When** 解析，**Then** 拒絕並指出那個名稱。
3. **Given** 函式參數個數不符的規則，**When** 解析，**Then** 拒絕並指出該呼叫。
4. **Given** 量綱不合的規則（例如拿電量百分比和距離公尺比較、把秒加到公尺上），**When** 解析，**Then** 拒絕並指出兩側各自的量綱。

### User Story 3 - 時序與趨勢規則解析成語法樹 (Priority: P2)

作為引擎開發者，我寫下時序約束與趨勢外推的規則（語料的後 10 條），引擎把「前一筆」「持續 N 秒」「N 秒內必須發生」
「與 N 秒前比較」「最近 N 秒的視窗」「外推到 N 秒後」這些概念解析成語法樹上明確的節點——M1 只解析，不評估。

**Why this priority**: 語法是本專案最難反悔的決定（憲章原則 III）。時序與視窗的語法若留到 M3 才設計，
基本規則的語法可能已經容不下它們，而那時 Evaluator 已經建在舊語法上。

**Independent Test**: 對 10 條時序與趨勢規則各自解析，與預期語法樹逐條比對；每個時間概念都對應到語法樹上一種可辨認的節點。

**Acceptance Scenarios**:

1. **Given** `battery-tier-low` 的規則文字，**When** 解析，**Then** 語法樹明確區分「條件」「持續時間」與「持續成立後必須滿足的要求」三個部分。
2. **Given** `battery-tier-emergency` 與 `battery-tier-critical`，**When** 解析，**Then** 「N 秒內必須發生」與「持續 N 秒」是兩種不同的節點。
3. **Given** `battery-runout-forecast`，**When** 解析，**Then** 視窗長度、被外推的量、目標門檻與比較的另一側各自是語法樹上可辨認的子樹。

---

### User Story 4 - 看得見語法樹與文法 (Priority: P3)

作為從實作反推理論的學習者，我要能看到每條語料規則的語法樹圖，並能從文法文件追到「這條產生式是哪幾條規則需要的、
由哪一個解析步驟處理」，以及這種解析方法在解決什麼問題的白話說明。

**Why this priority**: 憲章把視覺化定為學習基礎設施（語法樹結構是第一個例子），原則 IV 要求解析理論附白話橋接、
手寫解析器與形式文法的對應要寫明。它不影響解析正確性，所以排在正確性之後，但不延後到 M5。

**Independent Test**: 為 17 條語料規則各產出一張語法樹圖；從文法文件任挑一條產生式，能找到需要它的語料規則與處理它的解析步驟。

**Acceptance Scenarios**:

1. **Given** 任一條語料規則，**When** 產出語法樹圖，**Then** 每個節點標示種類與對應的原文片段。
2. **Given** 文法文件中的任一條產生式，**When** 查閱，**Then** 它列出需要它的語料規則短名與處理它的解析步驟。

---

### Edge Cases

- 空白規則（運算式只有空白）：MUST 以明確錯誤拒絕，不得產生空語法樹。
- 串接比較（例如「0 < x < 10」）：MUST 明確定義為接受並展開成兩個比較的「且」，或拒絕；
  不得默默解析成「(0 < x) < 10」。
- 一元負號與減號相鄰（例如「a - -b」、高度的「-D」）：語法樹 MUST 區分兩者。
- 深層巢狀括號：解析結果正確，或以明確錯誤拒絕，不得當機。
- 數字格式：小數、負數 MUST 支援；其他格式（例如科學記號）不支援時 MUST 以明確錯誤拒絕。
- 持續時間、期限或視窗長度為 0 或負數：寫成常值時 MUST 在解析時拒絕；寫成具名門檻時，值在 M2 綁定時檢查。
- 同一名稱同時是欄位與函式：MUST 不可能發生，或有明確的優先規則。
- 規則文字裡的裸數字常值（例如 `monotonic-sequence` 的「加 1」）：MUST 有明確的量綱規則，例如視為無因次。
- 第一筆事件沒有前一筆、時間差為 0、視窗未填滿：屬於評估語意，M1 只要求語法能表達，處置交給 M2／M3（見 Scope Boundaries）。

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 規則語料 MUST 納入版控，至少涵蓋 [rule-corpus.md](rule-corpus.md) 的 17 條，分屬門檻比較、邏輯組合、時序約束、趨勢外推四類；
  每條含短名、白話意圖、類別、規則文字與預期語法樹，並作為 parser 的回歸測試集，每次變更全數重跑。
- **FR-002**: 文法 MUST 以類 EBNF 記法納入版控；每條產生式 MUST 列出需要它的語料規則短名，並對應到一個可指認的解析步驟。
- **FR-003**: 系統 MUST 把合法規則文字轉成語法樹；每個節點 MUST 記錄它在原文中的起訖位置（行與欄）。
- **FR-004**: 規則 MUST 能表達比較（小於、小於等於、大於、大於等於、等於、不等於）、邏輯（且、「若 A 則 B」）、
  四則運算、一元負號、括號分組，以及函式呼叫（可巢狀、參數可以是任意運算式）。「或」與「非」不在 M1 文法內，
  但 MUST 是保留字：規則用到它們時以專屬錯誤拒絕，名稱也不得使用它們（user 2026-10-28 裁示，理由見 research Decision 2）。
- **FR-005**: 規則 MUST 能引用遙測欄位、向量欄位的分量，以及由欄位推得的衍生量；
  語料要求的衍生量至少有：高度、水平速度、離家水平距離。
- **FR-006**: 規則 MUST 能表達分段要求（「A 時要求 B，否則要求 C」），可透過條件式或多個蘊含，由 plan 決定。
- **FR-007**: 規則 MUST 能表達下列時間概念：前一筆事件的值、相鄰事件的時間差、條件持續成立 N 秒、
  N 秒內必須發生、與 N 秒前的值比較。
- **FR-008**: 規則 MUST 能表達下列趨勢概念：最近 N 秒視窗內的平均變化率、依視窗趨勢外推 N 秒後的值、
  依視窗趨勢外推到達某門檻所剩的時間、依目前速度外推未來位置。
- **FR-009**: 規則中的門檻 MUST 能以名稱引用，值由規則以外提供；M1 只解析與檢查名稱，不綁定數值。
  語料中所有待定數字都以具名門檻表示。
- **FR-010**: 規則引用的每個名稱 MUST 屬於已宣告的詞彙（遙測欄位、衍生量、函式及其參數個數、具名門檻）；
  未宣告的名稱與參數個數不符 MUST 被拒。
- **FR-011**: 無效規則 MUST 被拒，回報第一個錯誤的行、欄與原因，且不產生語法樹；不要求錯誤恢復（決策 002）。
- **FR-012**: 同一份規則文字 MUST 永遠產生相同的語法樹，且語法樹 MUST 有正規序列化，供回歸比對。
- **FR-013**: 詞彙表中每個欄位、衍生量、具名門檻與函式（參數與回傳值）MUST 宣告單位；解析時 MUST 推導每個子運算式的量綱，
  拒絕量綱不合的比較、加減與函式參數。規則文字不寫單位（user 2026-10-28 裁示）。
- **FR-014**: 系統 MUST 能為任一條合法規則產出語法樹圖，節點標示種類與對應的原文片段。
- **FR-015**: 解析方法 MUST 附出處與白話橋接（解決什麼問題、關鍵直覺、理論術語與本專案資料結構的對應），
  並寫明文法產生式與解析步驟的對應（憲章原則 IV）。
- **FR-016**: Fuzzer 套件 MUST NOT 引用 DSL 的語法樹或解析程式碼（憲章原則 I，GAR-21 的獨立性前提）；既有的架構邊界測試 MUST 持續涵蓋這一點。

### Scope Boundaries

- M1 不評估規則、不讀取遙測流、不維護時間視窗，也不判定違規；這些屬於 M2（GAR-19）與 M3（GAR-20）。
- M1 不決定任何門檻的數值，也不修改 M0 的 simulator 或情境。
- 解析在規則載入時進行一次，不在每筆事件的處理路徑上；M1 不做延遲宣稱，也不受憲章延遲階梯約束。
- 交給 M2（GAR-19）的已知事項：
  - `descent-speed-near-ground` 與 M0 `normal-flight` 的 1 m/s 等速落地衝突（user 2026-10-28 裁示留到 M2）。
  - 只在事件到達時檢查的規則抓不到資料流整個停止（`telemetry-heartbeat`）——偵測「安靜」需要不靠事件推進的時鐘。
  - 第一筆事件沒有前一筆、相鄰時間差為 0 時的語意。
- 交給 M3（GAR-20）的已知事項：視窗未填滿時的語意；趨勢外推的誤報可接受度（GAR-20 本身已要求在 specify 階段定義）。

### Key Entities

- **規則語料**：版控的規則集合與版本；每條規則有短名、類別、白話意圖、規則文字、預期語法樹。
- **規則**：一段規則文字與它的短名；解析成功得到一棵語法樹，失敗得到一個解析錯誤。
- **語法樹**：由節點組成的樹；節點種類至少涵蓋常值、具名門檻、欄位與分量、衍生量、函式呼叫、算術、比較、邏輯，
  以及 FR-007／FR-008 的時間與趨勢概念；每個節點帶原文位置。
- **詞彙表**：解析時可用的名稱宣告——遙測欄位、衍生量、函式（含參數個數）、具名門檻，各自帶單位。
- **文法**：類 EBNF 的產生式集合；每條產生式連到需要它的語料規則與處理它的解析步驟。
- **解析錯誤**：行、欄、原因，以及造成錯誤的原文片段。

## Success Criteria *(mandatory)*

### Measurable Outcomes

解析能力以階梯衡量（憲章的階梯原則），每階以它能處理的語料子集命名；Gate 是最寬鬆的一階，所有判定只收實測（E1）。

| 階 | 涵蓋的語料 | 條數 | 角色 |
|---|---|---|---|
| 基本規則 | 門檻比較＋邏輯組合 | 7 | Gate（GAR-18 驗收「可解析基本規則」） |
| 時序規則 | ＋時序約束 | 13 | 中間階 |
| 全語料 | ＋趨勢外推 | 17 | 頂階 |

- **SC-001**: 「基本規則」階：7 條規則 100% 解析成與預期完全一致的語法樹。
- **SC-002**: 「時序規則」階：13 條規則 100% 解析成與預期完全一致的語法樹。
- **SC-003**: 「全語料」階：17 條規則 100% 解析成與預期完全一致的語法樹。
- **SC-004**: M1 完成時 MUST 達到頂階「全語料」（user 2026-10-28 裁示）；Gate 與中間階是途中的可驗收點，不是完成條件。
- **SC-005**: 無效規則集對 User Story 2 與 Edge Cases 列出的每一類錯誤至少各有 2 個案例；100% 被拒、0 個產生語法樹，
  且回報的位置落在造成錯誤的那一段文字上。
- **SC-006**: 文法的每一條產生式都至少被 1 條語料規則用到（0 條沒有語料需要的產生式），每條語料規則都列出它用到的產生式。
- **SC-007**: 每一組優先序相鄰的運算子，至少有 1 個案例的語法樹會因兩者優先序對調而不同；故意把任一組優先序改錯時，回歸測試至少 1 條失敗。
- **SC-008**: 17 條語料規則各解析 3 次，語法樹的正規序列化 100% 相同。
- **SC-009**: 不讀程式碼，審查者能從語法樹圖中，對每條規則指出白話意圖的每個子句對應哪一棵子樹。

## Assumptions

- 規則作者是引擎開發者本人，規則以純文字撰寫；沒有圖形化編輯器。
- 「家」是 NED 原點，也就是起飛點（M0 的座標約定）；遙測本身不帶家的座標。
- 語料中的數字以具名門檻表示，實際值在 M2／M4 選定情境基準時綁定（user 2026-10-28 選「形狀先定、數字標待定」）。
- 規則文字的符號與名稱使用 ASCII；白話意圖寫在語料檔。
- 解析策略沿用決策 `docs/decisions/002-staged-python-parser-strategy.md`：手寫、不依賴解析器產生器；
  只有語料證明手寫無法清楚表達時才重新評估。
- 錯誤恢復不在範圍內：回報第一個錯誤即可（決策 002 已接受這個代價）。
